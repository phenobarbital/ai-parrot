# Feature Specification: Admin UI accepts every upload the backend stores, and reports what it stored

**Feature ID**: FEAT-739
**Date**: 2026-10-24
**Author**: agent:sdd-fix
**Status**: approved
**Target version**: 0.29.x

> Ledger-driven fix (`/sdd-fix`). Group `fixgroup:6630fd230436`,
> issue `issue:04dcfd611ebc` (feature_gap, major, discovered-from spec:FEAT-639).

---

## 1. Motivation & Business Requirements

### Problem Statement

FEAT-639 made the backend persist **every** uploaded file, not only tabular ones,
and replaced the upload response with an honest report. Two gates in the admin UI
were left behind, so the use case FEAT-639 exists to fix is still unreachable from
the admin UI:

1. **The picker blocks non-Excel files.** `DataManagementModal.svelte:109` rejects
   client-side anything that does not end in `.xlsx`/`.xls`
   ("Only Excel files (.xlsx, .xls) are allowed."), and the `<input accept=".xlsx">`
   at line 249 hides everything else in the OS file dialog. A `.docx` or `.pdf` can
   never be uploaded through the admin UI even though
   `BasicAgent.handle_files` (`packages/ai-parrot/src/parrot/bots/agent.py:377-449`)
   persists any byte string to the session store.
2. **The response is discarded.** `DataManagementModal.svelte:122-123` awaits
   `uploadAgentData` and then shows a hardcoded `"Uploaded"`. The user is told
   "success" by a string that is not derived from the server's answer, so a
   partially-failed upload reads as a clean one.

A third consequence falls out of (2): the handler answers **400** when nothing was
stored, with the per-file reasons in `errors`. The axios interceptor
(`http.ts:126-160`) turns that into `ApiError`, and `extractServerMessage` finds no
`error`/`message`/`detail` key in that body, so the user currently sees the literal
string `HTTP 400` instead of why the file was rejected.

### Goals

- G1. Any file the backend will accept can be chosen and uploaded from the admin UI.
- G2. The status line is derived from the server's response — stored files,
  registered dataframes, and per-file errors — never from a fixed string.
- G3. A 400 "nothing stored" response surfaces its per-file reasons, not `HTTP 400`.
- G4. A partial result (some files stored, some rejected) is visually distinct from
  a clean success.

### Non-Goals (explicitly out of scope)

- Multi-file upload. The modal sends `uploadFiles[0]` and the form field is single;
  that stays as it is.
- Any change to the backend, the handler, or `BasicAgent.handle_files`. FEAT-639
  already landed; this feature only catches the UI up.
- Client-side size validation. The session store owns the cap (FEAT-643, 25 MB)
  and reports it per file.
- Rendering `file_id` affordances (attach-by-handle, preview, delete). Out of scope.

## 2. Architectural Design

### Overview

The server is the only gate. The UI stops guessing which extensions are legal,
and instead renders the report the server already returns. One pure formatter
turns an upload payload into the status the modal shows, and it is reached from
both the success path and the 400 path, because both carry the same payload shape.

### Component Diagram

```
DataManagementModal.handleUpload()
      │
      ├─ ok  ─────────────→ uploadAgentData() ──→ AgentUploadResponse ─┐
      │                                                                 ├─→ formatUploadStatus() ─→ { type, message }
      └─ ApiError(400) ──→ err.raw.response.data (same shape) ─────────┘
```

### Integration Points

| Existing Component | Integration Type | Notes |
|---|---|---|
| `uploadAgentData` (`$lib/api/agent`) | types | gains a declared return type; the request itself is unchanged |
| `ApiError` (`$lib/api/http`) | reads | `raw.response.data` is the preserved body (`http.ts:59-72`) |
| `AgentTalk._handle_attachments` | consumes | response `{files, dataframes, errors, agent}`; 400 when nothing stored |

### Data Models

```ts
// packages/ai-parrot-server/ui/src/lib/api/agent.ts
export interface AgentUploadFileRecord {
  file_id: string;
  filename?: string;
  [key: string]: unknown;   // SessionFileRecord carries more; the UI reads these two
}

export interface AgentUploadFileError {
  filename: string;
  error: string;
}

export interface AgentUploadResponse {
  files: AgentUploadFileRecord[];
  dataframes: string[];
  errors: AgentUploadFileError[];
  agent?: string;
}
```

### New Public Interfaces

```ts
// packages/ai-parrot-server/ui/src/lib/components/agents/upload-status.ts
export type UploadStatusType = "success" | "warning" | "error";

export interface UploadStatus {
  type: UploadStatusType;

```

### Module 1: Upload status formatter

- **Path**: `packages/ai-parrot-server/ui/src/lib/components/agents/upload-status.ts` (new)
- **Responsibility**: the single place that decides what an upload result says and
  which colour it is. Pure, synchronous, no Svelte, no network — so it is unit
  tested without rendering.
- **Depends on**: the `AgentUploadResponse` types from M2.
- **Contract**:
  - `formatUploadStatus(payload)`:
    - `files.length > 0 && errors.length === 0` → `type: "success"`.
    - `files.length > 0 && errors.length > 0` → `type: "warning"`.
    - `files.length === 0` → `type: "error"`.
    - Message grammar, parts joined with `" · "`:
      - stored: `Stored <n> file(s)` — omitted when `files` is empty.
      - dataframes: `registered as dataset(s): <a>, <b>` — omitted when empty.
      - errors: `<filename>: <error>` per entry, joined with `"; "`.
    - A payload that is not an object, or whose `files`/`dataframes`/`errors` are
      missing or not arrays, is treated as **no information**: returns
      `{ type: "error", message: "Upload failed." }`. It never throws.
  - `uploadPayloadFromError(error)`: returns `error.raw.response.data` when every
    hop is present, otherwise `undefined`. It never throws.

- **Interface Skeleton**:
  ```ts
  // packages/ai-parrot-server/ui/src/lib/components/agents/upload-status.ts  (new)
  import type { AgentUploadResponse } from "$lib/api/agent";

  export type UploadStatusType = "success" | "warning" | "error";
  export interface UploadStatus { type: UploadStatusType; message: string; }

  export function formatUploadStatus(payload: unknown): UploadStatus {
    /** Derive the status line from an upload payload; never throws. */
  }

  export function uploadPayloadFromError(error: unknown): unknown {
    /** Return the preserved response body of an ApiError, or undefined. */
  }
  ```

### Module 2: Typed upload client

- **Path**: `packages/ai-parrot-server/ui/src/lib/api/agent.ts` (modifies, line 153)
- **Responsibility**: declare the three interfaces of §2 and give `uploadAgentData`
  the return type `Promise<AgentUploadResponse>`.
- **Depends on**: nothing.
- **Constraint**: the request (`PUT ${BASE_PATH}/${agentName}`, multipart) is
  **unchanged** — this is a typing change only. `src/lib/types/generated/` is
  produced by `pnpm generate` and is NOT touched.

### Module 3: Modal wiring

- **Path**: `packages/ai-parrot-server/ui/src/lib/components/agents/DataManagementModal.svelte` (modifies)
- **Responsibility**: drop the client-side gate, widen the picker, render the report.
- **Depends on**: M1, M2.
- **Decided changes**:
  1. `uploadStatus` state type widens from `"success" | "error" | null` to
     `UploadStatusType | null`.
  2. `handleUploadExcel` → `handleUpload` (and the `onclick` at line 255). The
     empty-selection guard stays verbatim. **The `.xlsx`/`.xls` check at lines
     108-115 is deleted.**
  3. Success path: `const result = await uploadAgentData(agentId, formData);`
     then `uploadStatus = formatUploadStatus(result);`. Clear `uploadFiles` only
     when `uploadStatus.type !== "error"`. The 3-second auto-clear runs **only**
     when `type === "success"`, so a warning or an error stays on screen.
  4. Catch path: `const payload = uploadPayloadFromError(error);` — when it is
     present use `formatUploadStatus(payload)`, otherwise fall back to
     `{ type: "error", message: error.message || "Upload failed." }`. The existing
     `console.error("Upload Error", error)` stays.
  5. Markup: `accept=".xlsx"` (line 249) is **removed** so the OS dialog shows every
     file. Copy changes: `Upload Excel` → `Upload File`; `Upload .xlsx file as
     dataset` → `Any file is stored for the agent; .xlsx, .xls and .csv also
     register as datasets`; `Click to choose .xlsx file` → `Click to choose a file`.
  6. The status paragraph's class picks three colours instead of two:
     `error` → `text-red-500`, `warning` → `text-amber-500`, `success` →
     `text-green-500`.

## 7. Implementation Notes & Constraints

### Patterns to Follow

- **Svelte 5 runes only** (`$state`, `$derived`, `$props`). The modal already uses
  them; never introduce `export let`.
- TypeScript `strict`. `formatUploadStatus` takes `unknown` and narrows — it must
  not assume the shape it was handed.
- Styling is Tailwind utilities, matching the surrounding classes. `text-amber-500`
  is the warning colour; do not invent a new palette entry.
- Tests are `vitest` + `@testing-library/svelte` next to the code, following the
  `vi.mock("$lib/api/...")` idiom of `MyToolkitSettings.test.ts`.
- No prettier/eslint step exists — match the surrounding formatting by hand.

### Known Risks / Gotchas

- **The 400 path is the one that is easy to get wrong.** `extractServerMessage`
  returns the literal `"HTTP 400"` for the upload body because it has no
  `error`/`message`/`detail` key. Reading `error.message` alone therefore loses
  every per-file reason — the reasons are only in `raw.response.data.errors`.
- `safeRaw` is deliberately lossy; only `message`, `code`, `response{status,
  statusText,data}` and `request{...}` survive. Do not reach for anything else.
- Removing `accept` widens the OS dialog to every file. That is intended: the
  session store, not the browser, decides what is legal, and it reports per file.
- The 3-second auto-clear must not swallow a warning or an error.

### External Dependencies

None. No new npm package.
