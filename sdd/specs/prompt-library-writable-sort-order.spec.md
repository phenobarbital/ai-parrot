## 1. Motivation & Business Requirements

### Problem Statement

`/api/v1/prompt_library` (`PromptLibraryManagement`) **cannot create a prompt today, for anyone**. A live smoke on
staging (2026-11-02, as an authenticated user, on a Studio agent UUID) failed twice:

1. `PUT` without `prompt_category` → `400`, *"Field prompt_category expected a string, got
   <PromptCategory.OTHER: 'other'> of type PromptCategory"*. The model's own default is an enum member, and the field
   is typed `str` under `strict = True`. FEAT-167's own test already knew this and worked around it
   (`packages/ai-parrot/tests/handlers/test_prompt_library.py:35`, *"use string value; Enum default has pre-existing
   issue"*).
2. `PUT` with `"prompt_category": "other"` → `400`, *"Error on Insert over table prompt_library: column "agent_id"
   does not exist"*. FEAT-167 (TASK-1133) added `agent_id` to the model and only *documented* the `ALTER TABLE` in the
   model docstring. The DDL was never applied: staging and production have no `agent_id` column, and the INSERT names
   every model field.

Updates go through `updating(**result.to_dict())`, which uses the same field list, so they are expected to fail the
same way. This was not tested live, to avoid writing to a real `ai_bots` row. GET works.

Consequence: `statics/ai` has not been able to create public prompts since FEAT-167 shipped (the newest row in both
databases is from 2025-09). The navigator-svelte companion feature, public "starter" prompts for Agent Studio agents,
has nothing to write through.

That companion feature also needs **manual order**: the first 5 prompts by order are the chat's welcome-screen
suggestions. `prompt_library` has no order column.

Two smaller defects on the same write path:
- `PromptLibraryManagement._set_created_by` (`handlers/bots.py:94`) runs on every write and fills `created_by` with
  the current user whenever the body lacks it. **Every edit or reorder rewrites the author to the editor.**
- `updated_at` is never refreshed on update (`default=datetime.now` only applies on construction).

### Goals
- G1. Create, partial update and delete through `/api/v1/prompt_library` work against the real staging/production
  schema.
- G2. `navigator.prompt_library` gains a nullable `sort_order integer`, and the model exposes it. It is readable and
  writable through the existing endpoint.
- G3. The schema change ships as Studio migration `0009` (the only DDL mechanism that is actually applied in every
  environment), and `STUDIO_SCHEMA_REQUIRED` moves to 9.
- G4. An update never changes `created_by`; every update sets `updated_at`.

### Non-Goals (explicitly out of scope)
- Authorization on `/api/v1/prompt_library` writes (today any authenticated user can write any chatbot's prompts).
  Accepted for now; tracked as a follow-up.
- New Studio routes for prompts (`/agents/{name}/prompts`); navigator-agent-studio allow-list changes.
- FEAT-167's `CHECK` (exactly one of `chatbot_id` / `agent_id`) and its `UNIQUE (chatbot_id, agent_id, title)`: see
  Open Questions Q2.
- Deleting an agent's prompts when the Studio agent is deleted (follow-up).
- Any UI. The UI is the navigator-svelte companion spec.

## 2. Architectural Design

### Overview

Four small changes, one release:

1. **Migration `0009_prompt_library_agent_id_sort_order.sql`** in the Studio migrations package: the advisory lock,
   `ALTER TABLE IF EXISTS navigator.prompt_library ADD COLUMN IF NOT EXISTS agent_id varchar`,
   `ADD COLUMN IF NOT EXISTS sort_order integer`, and the `-- @studio-ledger` trailer. `IF EXISTS` on the table is
   required: every Studio test database (`TEST_STUDIO_PG_DSN`) and the FieldSync raw per-file runner apply all
   packaged migrations to databases that may have no `prompt_library`, and a plain `ALTER TABLE` would abort the chain. `MANIFEST.json` gets the entry
   and `"required": 9`; `STUDIO_SCHEMA_REQUIRED = 9`. Checksums are written by the release tool
   (`parrot-studio-migrate --stamp`), never by hand.
2. **`PromptLibrary`** gains `sort_order: Optional[int]`, and `prompt_category`'s default becomes the string
   `PromptCategory.OTHER.value`.
3. **`PromptLibraryManagement`** keeps `created_by` on update and stamps `updated_at` on every write.
4. **The Studio cross-spec contract** (row X1, identical in three specs and pinned by a test) and
   `docs/agentstudio/db-storage.md` move from "versions 1..8" to "1..9", naming `prompt_library` as an existing,
   non-Studio table that `0009` extends in place.

**Why the column and the model field must ship together.** `ModelView.get` → `PromptLibrary.filter()` → asyncdb
`pg._filter_` runs `SELECT *` and builds `cls(**dict(row))` (`asyncdb/models/model.py:344`). Under `strict = True`,
an unknown key raises `TypeError: __init__() got an unexpected keyword argument 'sort_order'` (reproduced on the
model). A `sort_order` column without the field breaks every `/api/v1/prompt_library` read, for every chatbot.

**Why a Studio migration for a non-Studio table.** `prompt_library` is ai-parrot's table (the model lives here), but
ai-parrot has no other applied DDL mechanism. FEAT-167's docstring DDL is the proof: it was never run. The Studio
ledger is applied by Juan with `parrot-studio-migrate` (or navigator-agent-studio's wrapper) in every environment, and
the storage probe makes a missing version visible. This needs the Studio owner's sign-off (Open Questions Q1).

## 7. Implementation Notes & Constraints

### Patterns to Follow
- Migration format exactly as `0008_ai_user_toolkit_overrides.sql`: lock first, DDL, `-- @studio-ledger` trailer;
  checksum over the body only. Generate trailer and manifest with `parrot-studio-migrate --stamp`.
- Additive and idempotent only (`ADD COLUMN IF NOT EXISTS`). No data backfill: `sort_order` NULL means "unordered",
  and the reader sorts `sort_order NULLS LAST, created_at`.

### Known Risks / Gotchas
- **Strict model + `SELECT *`.** The column and the field ship in the same release (see Overview).
- **Deploy order (production Studio is live).** Decided: **apply `0009` first, then roll out the release
  immediately**, in one window. During the gap the old pods' legacy GET fails (strict model sees `sort_order`), but
  Studio stays up. The reverse order would put Studio storage `unavailable` for every tenant until the migration runs.
  Juan runs both.
- **`_set_created_by` and `NotSet`.** `ModelView._post_data` calls the hook for every column and writes its return
  value into the body. Returning `None` on update would make `_set_update` write `created_by = None`. Raising `NotSet`
  makes `set_column_value` **return early**, skipping every later column's hook. The task must pick a mechanism that
  leaves `created_by` out of the update dict (or restores the stored value) without either side effect, and prove it
  with `test_prompt_library_partial_update_keeps_fields_and_author`.
- **POST to a deleted `prompt_id`** falls into `NoDataFound` and tries an insert from the partial body. Without
  `title` / `query` the model rejects it. That is acceptable, but do not "fix" it into a silent insert.
- **Cross-spec contract test.** The three X1 rows must stay byte-identical; edit one, copy it to the other two.

### External Dependencies
None new.
