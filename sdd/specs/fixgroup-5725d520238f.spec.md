## 1. Motivation & Business Requirements

### Problem Statement

FEAT-648 made the four shelf-based planogram types opt in to slot-presence
reporting (`ReportingPolicy(slot_presence=True)` on their default layout
profile), so every product-detecting type reports `products_found`.

Three of the types that run on the shared cycle — `ProductOnShelves`,
`EndcapBacklitMultitier` and `InkWall` — define a private `_ensure_layout(ctx)`
helper and call it at the top of `perceive()`, `identify()` and `compare()`.
When the orchestrator (`plan.py`) has not populated `ctx.layout`, the helper
resolves the type's default profile merged with `planogram_config` through
`resolve_layout_profile()`, so a direct call to the type hook behaves like the
production path.

`ProductCounter` and `GraphicPanelDisplay` do **not** define that helper. A
direct `type.compare(..., ctx)` with `ctx.layout=None` reaches
`effective_reporting(ctx.layout, definition)` with `layout=None`, which falls
back to the global `ReportingPolicy()` default (`slot_presence=False`), and the
result carries `products_found == []`. Reproduced on `dev` @ `ab76c651a` with
the FEAT-648 test helpers:

| Type | `hasattr(handler, "_ensure_layout")` | `len(products_found)` |
|---|---|---|
| `endcap_backlit_multitier` | True | 3 |
| `product_counter` | False | 0 |
| `graphic_panel_display` | False | 0 |

The production path is unaffected (`plan.py` always passes the resolved
layout), so only direct callers and tests observe the gap. FEAT-648 also
verified these two types only at profile level
(`test_shelf_types_opt_in_to_slot_presence`), never through `compare()`, which
is why the inconsistency survived review.

### Goals

- **G1** — `ProductCounter` and `GraphicPanelDisplay` resolve their own layout
  profile when `ctx.layout is None`, exactly like `ProductOnShelves`,
  `EndcapBacklitMultitier` and `InkWall` (same helper name, same
  `resolve_layout_profile()` call, same call sites).
- **G2** — A `compare()`-level test per type proves the tri-state
  `products_found` report with `ctx.layout=None`, closing the verification gap.
- **G3** — Close `issue:0a49138a5ac3` with real evidence (a diff touching the
  two type files plus a passing validation run), never by assertion alone.

### Non-Goals (explicitly out of scope)

- Hoisting `_ensure_layout` into `AbstractPlanogramType`. Five types would
  then share one helper, but `EndcapNoShelvesPromotional` and the abstract
  contract (`_CYCLE_HOOKS`, `validate_contract()`) are untouched by the
  ledger issue; a base-class refactor is a design change with its own blast
  radius and belongs in a separate spec.
- Any change to `plan.py`, `stages/compare.py`, `effective_reporting()` or the
  `ReportingPolicy` resolution order (documented in
  `docs/pipelines/planogram-compliance-cycle.md` §ReportingPolicy — that text
  stays correct).
- Documentation changes. The docs describe behaviour, not the private
  helper, and the behaviour does not change for the production path.

## 2. Architectural Design

### Overview

Copy the established helper verbatim into the two types and call it at the
top of each cycle hook:

```python
def _ensure_layout(self, ctx: CycleContext) -> LayoutProfile:
    """Resolve defaults and configuration when the orchestrator has not populated the context."""
    if ctx.layout is None:
        ctx.layout = resolve_layout_profile(
            self.default_layout_profile(),
            dict(self.config.planogram_config or {}),
            config_name=str(getattr(self.config, "config_name", None) or type(self).__name__),
        )
    return ctx.layout
```

The orchestrator path is unchanged: `plan.py` sets `ctx.layout` before any
hook runs, so the helper is a no-op there.

### Component Diagram

```
plan.py ──(ctx.layout set)──→ ProductCounter.compare ──→ compare_observations ──→ effective_reporting(ctx.layout, …)
direct caller ──(ctx.layout=None)──→ ProductCounter.compare
                                        └─ _ensure_layout(ctx)  ← NEW: resolve_layout_profile(default, planogram_config)
```

### Integration Points

| Existing Component | Integration Type | Notes |
|---|---|---|
| `parrot_pipelines.planogram.layout.resolve_layout_profile` | uses | same call as `types/product_on_shelves.py:123` |

## 7. Implementation Notes & Constraints

### Patterns to Follow
- Copy the helper from `product_on_shelves.py:120-128` verbatim — same name,
  same docstring, same `getattr(self.config, "config_name", None)` fallback —
  so the five shared-cycle types stay byte-for-byte consistent.
- The hook docstrings stay as they are; only the first statement changes.
- Tests reuse the FEAT-648 module helpers; do not add a new conftest fixture.

### Known Risks / Gotchas
- The shared `.venv` is editable-installed against the main checkout, so
  `pytest` inside the worktree must be prefixed with
  `PYTHONPATH=packages/ai-parrot-pipelines/src:packages/ai-parrot/src` or it
  silently tests `dev`'s code.
- `ProductCounter._description()` / `GraphicPanelDisplay._description()` log a
  debug-level Pydantic error for configs without the ProductOnShelves-shaped
  keys; that is pre-existing and expected (the fallback description is used).

### External Dependencies

None — no new dependency.
