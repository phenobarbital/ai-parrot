# Brainstorm: Claude Code and Codex Tool Optimizations

**Date**: 2026-09-10
**Author**: Jesus Lara / Codex
**Status**: exploration
**Recommended Option**: B

---

## Problem Statement

Claude Code and Codex repeatedly spend model output tokens constructing predictable
Git command sequences, consume unnecessary source text, and use expensive reasoning
models to emit code whose design has already been decided. The intended users are
developers using these hosts and the SDD spec → task → implementation workflow.

The proposal covers three capabilities: deterministic Git operations, bounded source
reads, and TASK-scoped code generation through a configurable cheaper/local model.
All must be available as AI-Parrot tools in `ai-parrot-tools` (`parrot_tools`) and
through local stdio MCP, following the existing WikiToolkit installation pattern.

Reducing command construction alone may save little: tool schemas, tool results,
extra calls, contract preparation, delegated generation, and review all cost tokens.
Success must be measured over completed tasks, including failures and repairs.
Cheaper-model delegation can reduce cost and primary-model tokens while increasing
total tokens; these are separate metrics.

## Constraints & Requirements

- Exploration only. This document introduces no implementation, dependencies, host
  configuration changes, or production tool registrations.
- Flow defaults to `feature` / `dev`, as permitted by the brainstorm skill when
  unanswered. Other unanswered choices remain open rather than being treated as approval.
- Concrete implementations belong in `packages/ai-parrot-tools/src/parrot_tools/`.
  Use `AbstractTool` subclasses, including the existing `ToolkitTool(AbstractTool)`
  wrappers generated by `AbstractToolkit.get_tools()`.
- Reuse the existing local MCP server/configuration/installers. Each capability can
  be enabled independently and exposes a small, bounded schema surface.
- Git and source reading must work without any LLM. Writer calls go through an
  `AbstractClient`; local models use the existing local-client satellite.
- Python async interfaces, typed inputs/results, Pydantic validation, existing
  dependencies only. No Portal/AiKA service or new model SDK is required.
- Linked Git worktrees are first-class. Preserve unrelated working-tree content,
  staging intent, host permissions, and existing managed/foreign MCP entries.
- A size threshold applies to source reads: more than 350 lines **or** a configurable
  byte threshold requires an explicitly bounded request. Limits also apply to the
  response itself, including extremely long single lines.
- No claim that MCP registration forces the host to choose these tools. Skills and
  host hooks address routing; tool-side validation remains independently enforced.
- More detailed TASK files reduce guessing but cannot guarantee correct generated
  code. Verified contracts, patch checks, tests, and thinking-model review remain necessary.

## Options Explored

### Option A: Thin MCP facades over current tools

Wrap the existing Git, repository reader, and coding toolkits in three small
`parrot_tools` adapters. Add the minimum missing Git operations and read checks;
route usage mainly through SDD instructions. Retain the existing coding-provider
contract with limited TASK validation.

**Pros:** Fastest path to all three MCP capabilities; substantial existing behavior
and tests can be reused; little shared infrastructure changes.

**Cons:** Existing reader loads the entire file before slicing. GitToolkit is
GitHub-oriented and its pull validation misses linked worktrees. Existing coding
providers are not a ready-made TASK validator/apply pipeline. Host read tools can
bypass advisory routing. A thin wrapper still needs meaningful correctness work.

**Effort:** Medium.

**Libraries / Tools:**

| Package/tool | Purpose | Dependency evidence |
|---|---|---|
| Pydantic, stdlib `asyncio`/`pathlib` | Input validation and async filesystem/Git operations | Core Pydantic declaration; standard library |
| Existing MCP extra | Stdio exposure | `packages/ai-parrot/pyproject.toml:457` |
| `ai-parrot-client-local` | Configurable local generation | Existing satellite, `pyproject.toml:15` |

**Existing Code to Reuse:** `ReadOnlyRepoToolkit.read_file` at
`packages/ai-parrot/src/parrot/tools/repo/toolkit.py:200`, `GitToolkit.pull_repo`
at `packages/ai-parrot-tools/src/parrot_tools/gittoolkit.py:1653`, and
`CodeToolkit` at `packages/ai-parrot-tools/src/parrot_tools/code_toolkit.py:273`.

### Option B: Three focused toolkits with shared policy and TASK contracts

Build local Git, bounded source reader, and targeted writer toolkits on the current
MCP framework. Reuse repository confinement, Git history parsing, coding task/result
concepts, and client construction. Introduce a versioned delegation contract and
separate generation, review, and patch application. Add narrow host guards and SDD
routing instructions alongside tool-side limits.

**Pros:** Covers the complete request, supports local models, and makes mutation
scope and failure handling explicit. Avoids adding write behavior to the intentionally
read-only core toolkit. Independently configurable capabilities limit schema overhead.

**Cons:** Requires new policy tests, host integration tests, TASK-template changes,
and a writer validation path. Hooks still cannot promise universal interception.
Stricter contracts shift work to planning and may make small tasks uneconomical to delegate.

**Effort:** High for the whole initiative; Git and reader foundations can land first.

**Libraries / Tools:**

| Package/tool | Purpose | Dependency evidence |
|---|---|---|
| Pydantic, stdlib `asyncio`, `hashlib`, `pathlib`, `tempfile`, `difflib` | Contracts, process execution, revisions, patch artifacts | Existing Pydantic; standard library |
| `git` executable | Native repository operations and patch checks | Already used by GitToolkit and ReadOnlyRepoToolkit |
| Existing MCP extra and `LLMFactory` | Local serving and provider-neutral client injection | Core dependency declaration and factory source |
| Optional `ai-parrot-client-local` | User-configured local coder | Existing workspace package; endpoint/model availability must be checked |

**Existing Code to Reuse:** `create_toolkit_mcp_server` at
`packages/ai-parrot/src/parrot/mcp/toolkit_server.py:29`; confinement helpers at
`packages/ai-parrot/src/parrot/tools/repo/confinement.py:63`; `CodingProvider` at
`packages/ai-parrot-tools/src/parrot_tools/code_toolkit.py:55`; TASK contract sections
at `sdd/templates/task.md:43` and `:73`.

### Option C: Compile TASK files into deterministic edit recipes

The less obvious approach: the thinking model emits a validated, versioned edit
recipe with exact source revisions and bounded operations during task creation.
A deterministic writer applies literal replacements/patches; a cheaper model is
used only for recipe steps requiring generation. Git and reader MCP tools remain.

**Pros:** Routine changes can avoid a second model entirely. Explicit recipes make
scope, replay, and expected source state easy to inspect. Useful for repeated
boilerplate or highly mechanical changes.

**Cons:** The expensive planner may end up generating most of the code; recipes
become stale and need a new format/validator. Multi-file semantic changes remain
hard. This changes the SDD authoring contract more substantially than Option B.

**Effort:** High.

**Libraries / Tools:** Pydantic for a recipe schema, stdlib hashing/diff utilities,
Git patch checks, and the existing MCP/client infrastructure; no new package proposed.

**Existing Code to Reuse:** `CodingTask.files_in_scope` at
`packages/ai-parrot-tools/src/parrot_tools/code_toolkit.py:38`, TASK implementation
notes at `sdd/templates/task.md:73`, and the existing local MCP factory above.

---

## Recommendation

**Option B** best fits all three requested capabilities while preserving the current
SDD workflow and package boundaries. Treat the feature as one initiative, delivered
in dependency order: shared contracts/Git/reader, then writer/SDD integration, then
host guards and end-to-end measurements. Release bundling is still an open question.

Use toolkit-generated `AbstractTool` instances rather than inventing a separate tool
framework. Reuse current reader confinement and history utilities by composition;
do not add mutation methods to `ReadOnlyRepoToolkit`. Keep Option C as a later
optimization for tasks shown by measurements to be purely mechanical.

## Feature Description

### User-Facing Behavior

Names below are **proposed**, not existing APIs. Three capability families can
contain several narrowly named MCP tools; “three tools” is interpreted as the three
user-requested capabilities, not a constraint of exactly three callable methods.

| Capability | Proposed calls | Compact result |
|---|---|---|
| Local Git | `git_recent`, `git_fetch`, `git_preflight`, `git_prepare_files`, `git_pull`, `git_push` | Operation status, relevant refs/HEAD, bounded commits or file lists, checks and actionable errors |
| Bounded reading | `source_info`, `source_read`, optional `source_chunks` | Revision, returned range, bounded text, continuation and explicit truncation metadata |
| Targeted writing | `writer_generate`, `writer_apply` | Patch artifact identifier/hash, changed paths, provenance, validation state and bounded diagnostics |

The host calls named operations with arguments instead of constructing Bash
pipelines. Installation uses configured toolkit sections and the existing
`parrot claude install` / `parrot codex install` routes. A missing writer provider
must not disable deterministic Git or reading tools.

#### Git behavior

- `git_fetch(remote="origin", branch="dev", recent=3)` performs fetch and returns
  the fetched revision and bounded recent commits. A failed fetch cannot be hidden
  by a successful tail/log command. Return each completed step and preserve its exit status.
- `git_recent` is independently available for bounded history. Reuse existing
  history parsing instead of returning decorative log output.
- `git_preflight` reports short status, unstaged whitespace checks, staged paths,
  and optionally staged whitespace checks in one structured response. Run independent
  read-only checks even when one fails, making failure explicit in the aggregate.
- `git_prepare_files(paths=[...])` stages exact literal paths and verifies staged
  names and whitespace. Proposed default: refuse unrelated staged content; never
  silently reset the index. A replace-staging mode requires an explicit contract
  if selected during spec review. Partial staging of selected files must also be
  detected and reported before whole-file staging changes it.
- The user's reset/add/check sequence does not commit or push. Git push publishes
  commits reachable from refs, not individual filenames. Keep preparation, commit,
  and push distinct until the product owner resolves the intended workflow.
- Pull is fast-forward-only. Push uses explicit/default-validated remote and branch,
  with no force push. Missing upstream, divergence, detached HEAD, authentication
  failures, and rejected hooks produce concise recoverable errors.
- Discover repositories with Git, including linked worktrees; do not assume `.git`
  is a directory. Use argument arrays, literal path handling and validated refs,
  never caller-provided shell commands. Bound duration and output; scrub credentials.
- Mutating operations need per-worktree coordination and before/after state checks.
  Git locks remain authoritative; do not claim a toolkit lock excludes external Git
  processes. No automatic reset, stash, retry of an uncertain push, or destructive rollback.

#### Reader behavior

- Metadata or an unbounded request for a large source file returns a compact
  `range_required` result with size/threshold information and example arguments.
  An outline is optional and should reuse the wiki rather than load the full source.
- Canonical coordinates are 1-based inclusive `start_line`/`end_line`. If an
  offset/limit form is also exposed, define its base and reject mixed coordinate modes.
  Merely supplying an offset cannot unlock an unlimited response.
- Proposed defaults: threshold 350 lines, byte threshold 64,000, response capped
  by both lines and bytes. Byte defaults are provisional; exact serialized-response
  accounting and oversized-line continuation must be fixed in the spec.
- Chunking returns a manifest or one requested chunk with continuation. Never
  concatenate every chunk into a single model-visible response. Preserve source
  line numbers and return a revision/hash; stale continuation fails explicitly.
- Stream bounded portions or use bounded scans off the event loop. Avoid reading
  a multi-megabyte file fully just to slice it. Exact total line counts/hashes may
  require a scan; keep memory bounded and cache only against checked revisions.
- Preserve repo confinement and secret-file policy. Handle symlink escapes,
  non-regular files, binary input, decoding failures, empty files, invalid ranges,
  CRLF and long lines. Never silently present partial text as the full file.

#### Targeted writer and SDD behavior

- The thinking model still designs the feature in `sdd-spec` and creates precise
  tasks in `sdd-task`. Add a versioned, machine-checkable delegation section to TASK
  files alongside the existing Codebase Contract and Implementation Notes.
- Require exact allowed paths/actions, expected revisions for existing files,
  verified imports/signatures, bounded reference excerpts, concrete implementation
  guidance, expected behavior, edge cases, acceptance tests and validation commands.
  Include enough example code to demonstrate the intended pattern without forcing
  the thinking model to prewrite the entire solution. No invented APIs or empty placeholders.
- `sdd-start`/`sdd-worker` validates this packet before invoking the cheaper model.
  Missing/stale information returns `contract_incomplete`/`stale_context` to the
  thinking model. Existing TASK files remain usable by the normal implementation
  workflow; they are not automatically eligible for delegation.
- `writer_generate(task_path=..., ...)` reads the bounded packet locally and calls
  the configured `AbstractClient`. Qwen3-Coder is a user-requested candidate, not a
  verified installed model or promised quality level. Select and benchmark the exact
  hosted/local model and endpoint before enabling delegation.
- The cheap model has no arbitrary shell, Git mutation, dependency installation,
  or unrestricted file-writing authority. Treat its output as untrusted generated
  text. It returns a patch that is validated for syntax, scope and source freshness.
- Store patch artifacts locally and return their identity plus a compact summary.
  The thinking model retrieves changed hunks for review. Applying a patch requires
  the reviewed artifact hash and matching current revisions; an opaque artifact ID
  alone does not prove review. Host/user authorization follows the existing workflow,
  not a new mandatory human prompt on every task.
- Validate and apply all scoped changes with fail-closed preconditions; do not
  leave silently partial application. No surprise deletion, rename, binary edit,
  out-of-scope path, symlink traversal, or mutation of SDD state by the writer.
- Run actual tests through the authorized SDD validation path, with logs in
  `artifacts/logs/`. Model-generated claims that tests passed are not test evidence.
  A temporary validation worktree may be useful when a patch needs execution before
  approval. Respect dependencies already declared in project manifests.
- Proposed retry budget: one targeted repair using bounded diagnostics, then return
  to the thinking model. Do not silently escalate to a more expensive/remote model.
  Keep context, output-token, wall-time and retry budgets configurable and recorded.

### Internal Behavior

1. Three new `parrot_tools` toolkits share typed policy/result helpers. Method
   wrapping produces `AbstractTool` instances; deterministic methods never call an LLM.
2. MCP configuration selects toolkit class, constructor kwargs, tool allowlist and
   optional `llm`. The existing factory injects `llm_client` and omits unavailable
   LLM-dependent tools. The writer constructor must match that injection contract;
   `CodeToolkit(provider=...)` does not match it without an adapter.
3. Share small result envelopes: status, data, executed steps, error code, truncation,
   artifact references and measured usage where relevant. Keep full diagnostics on
   disk with bounded retrieval rather than echoing them into each response.
4. SDD prompts route relevant operations through the tools; host-specific hooks
   inspect supported full-file read paths and explain how to request a bounded range.
   Hook failures and coverage must be visible, not mistaken for successful enforcement.
5. Record Git/read calls, response bytes, primary/delegate tokens, latency, retries,
   acceptance/test outcomes and review corrections. Distinguish measured usage from
   estimates. Include tool-schema overhead and increased planning tokens in comparisons.

### Host Enforcement and External Research

Shunt provides the useful separation of hooks, deterministic invocation scripts,
and usage skills; its reader threshold defaults to 350 lines and its writer requires
a reference file. Its published savings are upstream claims, not measurements for
AI-Parrot. Adopt the separation of responsibilities, not its Portal/AiKA dependency.
[Shunt source and README](https://github.com/sorantis/portal-ai-plugins/tree/add-shunt-claude/plugins/shunt).

Claude Code documents `PreToolUse` decisions that can deny a tool call before it
executes. A guard can cover direct Read calls and selected Bash read patterns.
[Claude Code hooks](https://code.claude.com/docs/en/hooks).

Current Codex documentation also supports `PreToolUse` for shell/unified exec,
MCP and other local tools, including nested calls from code mode. It explicitly
notes exceptions and that `write_stdin` does not rerun the pre-hook. Verify the
installed host version/configuration and test its coverage; do not assume a
Claude-shaped hook is universally portable.
[Codex hooks and tool coverage](https://learn.chatgpt.com/docs/hooks).

Inference: MCP policy plus tested host guards can reduce accidental unbounded
reads, but cannot guarantee complete mediation of arbitrary shell programs or
every alternative tool. Comprehensive host-wide enforcement would be a separate,
larger host/sandbox integration. This limitation needs an explicit product decision.

### Edge Cases & Error Handling

| Failure | Required behavior |
|---|---|
| Git operation fails after an earlier step succeeded | Return completed steps and failing exit status; never report aggregate success |
| Remote push times out after possible acceptance | Report uncertain remote state; inspect refs before any retry |
| Unrelated/partially staged files | Refuse or require explicitly selected staging policy before changing the index |
| Read or TASK source changes during the operation | Detect revision mismatch and require fresh context |
| Single huge source line exceeds budget | Explicit bounded result/continuation or line-too-large error; no silent omission |
| Bad patch, scope escape, stale target | Reject before modifying checkout; retain bounded diagnostics |
| Missing/unavailable model or exhausted retry budget | Return actionable failure to the thinking model; deterministic tools still work |
| Host hooks unsupported or disabled | Report capability status; retain MCP validation and clearly describe routing limitation |

### Validation and Success Measurement

Use reproducible repositories/tasks: fetch plus recent history, clean/dirty preflight,
selected-file staging with unrelated and partial staging, linked-worktree pull/push,
large-file targeted reads, long-line input, and scoped boilerplate/modification tasks.
Include stale files, malformed patches, subprocess timeout and install/uninstall cases.

Compare baseline and optimized runs against identical fixtures and acceptance tests.
Report primary tokens, delegate tokens, total tokens, configured-price cost where
available, latency, call count, retries, and completion correctness. Do not adopt an
upstream savings percentage. The product owner must set quantitative release targets;
correctness and scope preservation are mandatory regardless of token savings.
