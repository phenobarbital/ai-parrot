# Brainstorm: Raw Upload Field Types (FEAT-460)

**Date**: 2026-08-25
**Author**: Jesus Lara / Claude
**Status**: exploration
**Recommended Option**: Option B

---

## Problem Statement

The FormBuilder's upload/media field types (`FILE`, `IMAGE`, `IMAGE_DROPZONE`,
`MULTI_UPLOAD`) have **fragmented and lossy value shapes**. When a user uploads a
file, metadata that is essential for downstream processing — MIME type, file size,
original filename, extension — is either lost entirely or scattered across
incompatible structures:

| Field Type | Value Shape | What's Lost |
|---|---|---|
| `FILE` | `string` (URL or base64) | mime_type, size, filename, extension, blob_ref |
| `IMAGE` | `string` (URL or base64) | mime_type, size, filename, extension, blob_ref |
| `IMAGE_DROPZONE` | `{name, type, size, dataUrl}` | blob_ref (server storage) |
| `MULTI_UPLOAD` | `[{answer, blob_ref, display}]` | mime_type, size, filename |
| `REST` | `{answer, blob_ref}` + BlobMetadata on backend | filename, extension in value |

**Who is affected:**

- **Form designers** — cannot build forms that accept PDFs, DOCX, HTML, Markdown as
  first-class uploads because `FILE`/`IMAGE` have no structured metadata.
- **Frontend developers** — must use side-channel hacks (`{field_id}__mime` in
  `all_data`) to access MIME type for `FILE`/`IMAGE` validation.
- **Backend consumers** — have no reliable way to reconstruct file metadata from
  stored submission values for `FILE`/`IMAGE`.
- **Agent/API consumers** — cannot programmatically determine what type of file was
  uploaded or its size without re-downloading the blob.

**Why now:** The platform needs to support document uploads (PDFs, contracts,
reports) alongside images. The current `FILE` type stores a string that could be
anything — a URL, a base64 blob, a filename — with no machine-readable contract.
Every new consumer must guess, parse, and hope.

## Constraints & Requirements

- **Backward compatibility**: Existing `FILE`/`IMAGE` submissions stored as strings
  MUST continue to be readable (dual-read: accept legacy string OR new
  FileEnvelope).
- **Any MIME type by default**: No hardcoded MIME restrictions. The existing
  `constraints.allowed_mime_types` controls per-field restrictions.
- **Dual storage**: The FileEnvelope always includes `blob_ref` (server-side storage
  via AbstractBlobStorage) and `data_url` (inline base64) up to a configurable
  threshold.
- **Inline size threshold**: `data_url` is included only when file size ≤ a
  configurable limit (default ~5MB). Over the threshold, only `blob_ref` is
  populated and the frontend fetches via GET.
- **Multi-file per request**: The upload endpoint accepts multiple `file` parts in a
  single multipart request.
- **Thumbnail support**: Optional `thumbnail_url` field in the envelope, generated by
  the backend for image types.
- **Align all upload types**: FILE, IMAGE, IMAGE_DROPZONE, and MULTI_UPLOAD all adopt
  the same FileEnvelope shape. Existing per-type value schemas become the envelope.
- **New dedicated endpoint**: A new `/file-upload` endpoint separate from the
  existing REST upload handler.
- **No breaking changes to REST type**: The `FieldType.REST` pipeline is untouched;
  it serves a different purpose (upload + external API callback).

## Options Explored

### Option A: Minimal — Enrich FILE/IMAGE Only

Introduce a `FileEnvelope` Pydantic model and apply it only to `FILE` and `IMAGE`
field types. Leave `IMAGE_DROPZONE` and `MULTI_UPLOAD` as-is.

The validator's `_coerce_value` for FILE/IMAGE would accept either a legacy string or
a FileEnvelope dict. The JSON Schema renderer would emit the new object shape. A new
upload endpoint handles the binary pipeline.

✅ **Pros:**
- Smallest scope — fewest files changed
- Zero risk of breaking IMAGE_DROPZONE/MULTI_UPLOAD consumers
- Fastest path to enabling document uploads (PDF, DOCX, etc.)

❌ **Cons:**
- Leaves the fragmentation problem half-solved — four different upload shapes
- IMAGE_DROPZONE's `{name, type, size, dataUrl}` remains a different shape
- MULTI_UPLOAD's `{answer, blob_ref, display}` remains a different shape
- Frontend teams maintain two code paths for "upload" fields

📊 **Effort:** Medium

### Option B: Unified FileEnvelope — Align All Upload Types (Recommended)

Define a single `FileEnvelope` Pydantic model as the canonical value shape for ALL
upload field types. FILE, IMAGE, IMAGE_DROPZONE, and MULTI_UPLOAD all converge on
this shape. The model lives in `parrot_formdesigner/core/file_envelope.py`.

**FileEnvelope shape:**

```
{
    "filename": "report-q3.pdf",                  # original name with extension
    "content_type": "application/pdf",            # MIME type
    "size": 183204,                               # bytes
    "blob_ref": "s3://bucket/form-uid/field-uid/uuid",  # server storage ref
    "data_url": "data:application/pdf;base64,...", # inline (null if over threshold)
    "thumbnail_url": "/api/v1/.../thumbnail/uuid", # optional, images only
    "checksum": "sha256:abc123..."                 # optional, integrity
}
```

**Value shapes per field type after migration:**

| Field Type | New Value Shape | Cardinality |
|---|---|---|
| `FILE` | `FileEnvelope \| string` (dual-read) | single |
| `IMAGE` | `FileEnvelope \| string` (dual-read) | single |
| `IMAGE_DROPZONE` | `FileEnvelope \| list[FileEnvelope] \| legacy` | single or multi |
| `MULTI_UPLOAD` | `list[FileEnvelope] \| legacy` | multi |

**Key behaviors:**

1. A new `FieldConstraints` field `max_inline_size_bytes` (default 5242880 = 5MB)
   controls the threshold for including `data_url`.
2. The validator's `_coerce_value` accepts legacy shapes for backward compatibility,
   normalizing them to FileEnvelope internally when possible.
3. A new upload endpoint `POST /api/v1/{tenant}/forms/{form_uid}/fields/{field_uid}/file-upload`
   handles the binary pipeline, returning one or more FileEnvelopes.
4. The JSON Schema renderer emits the FileEnvelope object schema for these types
   (replacing the bare `"type": "string"` for FILE/IMAGE).
5. All renderers (html5, pdf, xforms, adaptive_card, telegram) are updated to
   handle the envelope shape.

✅ **Pros:**
- **One shape to rule them all** — frontend teams learn one upload contract
- **Full metadata preservation** — mime, size, filename, extension always available
- **Backward compatible** — dual-read coercer accepts legacy strings
- **Future-proof** — adding VIDEO, AUDIO_FILE, etc. just reuses FileEnvelope
- **Reuses existing infrastructure** — AbstractBlobStorage, BlobMetadata, constraint fields
- **Enables document uploads** — PDF, DOCX, HTML, Markdown work immediately via
  `allowed_mime_types`

❌ **Cons:**
- Larger scope — touches validators, all 6+ renderers, JSON Schema type maps
- IMAGE_DROPZONE consumers must handle both `{name,type,size,dataUrl}` (legacy) and
  FileEnvelope (new) during transition
- MULTI_UPLOAD consumers must handle both `{answer,blob_ref,display}` and
  FileEnvelope during transition
- Breaking change for consumers that rely on `typeof value === 'string'` for FILE/IMAGE

📊 **Effort:** High

- `DOCUMENT = "document"` — single-file upload with full metadata (replaces

✅ **Pros:**

### Option D: Thin Wrapper — Upload Service Layer Without Value Shape Change

Keep all value shapes as-is. Instead, build an upload service layer that stores
metadata externally (in a `file_metadata` table or a sidecar JSON store keyed by
`blob_ref`). The field value stays a string/dict, but metadata is queryable
separately.

✅ **Pros:**
- Zero changes to validators, renderers, or JSON Schema
- Metadata available via API query even for legacy submissions

- Two sources of truth: the field value and the metadata store
- Frontend still can't show filename/size without an extra API call
- Adds operational complexity (metadata store must be kept in sync with blob storage)
- Doesn't enable document uploads in a first-class way

## Recommendation

**Option B — Unified FileEnvelope** is recommended because:

1. **It solves the fragmentation permanently.** The four upload types converge on
   one shape, which means one frontend component, one validation path, one
   serialization contract. Option A leaves the problem half-solved; Option C makes
   it worse by adding more types.

2. **Dual-read makes it non-breaking.** The coercer accepting legacy strings means
   existing submissions keep working without migration scripts. New submissions get
   full metadata. This is the same pattern used successfully for TREE_SELECT
   (`_UNION_SHAPES` — string or array).

3. **The infrastructure already exists.** AbstractBlobStorage (4 backends),
   BlobMetadata, `_stream_with_limit`, constraint fields — it's all there.
   We're wiring existing pieces into a new endpoint and value shape, not building
   from scratch.

4. **Future types are free.** VIDEO, AUDIO_FILE, 3D_MODEL, CSV — any future upload
   type just uses FileEnvelope. No new shapes to invent.

The tradeoff is scope: every renderer needs updating, and consumers must handle
the dual value shape during transition. But this is a one-time cost that pays off
permanently — Option A or D would accumulate the same total work spread across
multiple FEATs.

## Feature Description

### User-Facing Behavior

**For form designers:**
- FILE and IMAGE fields now support uploading ANY file type (PDF, DOCX, HTML,
  Markdown, etc.) — controlled via `allowed_mime_types` in constraints.
- A new `max_inline_size_bytes` constraint controls when inline base64 is included
  vs. server-only storage.
- The form-controls catalog (`GET /api/v1/form-controls`) reflects the new value
  shape in the `value_shape` field for FILE, IMAGE, IMAGE_DROPZONE, MULTI_UPLOAD.

**For end users filling forms:**
- Upload experience is unchanged — drag-and-drop or file picker.
- The uploaded file's name, type, and size are now preserved and displayed in the
  form UI (previously lost for FILE/IMAGE).

**For API/agent consumers:**
- Submission data for upload fields now returns a structured FileEnvelope with all
  metadata. Legacy string values continue to be accepted on input.

### Internal Behavior

**Upload flow (new endpoint):**

```
1. Client sends POST /api/v1/{tenant}/forms/{form_uid}/fields/{field_uid}/file-upload
   - multipart/form-data with one or more "file" parts
2. Handler resolves FormField via form_registry + find_field_by_uid
3. Handler validates field_type is in {FILE, IMAGE, IMAGE_DROPZONE, MULTI_UPLOAD}
4. For each file part:
   a. Detect MIME type from Content-Type header (optionally verify with python-magic)
   b. Validate against constraints.allowed_mime_types (415 if rejected)
   c. Stream with size limit via _stream_with_limit (413 if exceeded)
   d. Persist to AbstractBlobStorage → get blob_ref
   e. If size ≤ max_inline_size_bytes: encode as data_url
   f. If content_type starts with "image/": generate thumbnail → thumbnail_url
   g. Compute SHA-256 checksum
   h. Build FileEnvelope
5. Return JSON: single FileEnvelope or list depending on field cardinality
6. Handle X-Parrot-Prior-Blob-Ref for replacement uploads (delete old blob)
```

**Validation flow (dual-read coercer):**

```
1. _coerce_value receives value for FILE/IMAGE/IMAGE_DROPZONE/MULTI_UPLOAD
2. If value is a string → legacy path: accept as-is (backward compat)
3. If value is a dict → validate as FileEnvelope (required keys: filename,
   content_type, size; optional: blob_ref, data_url, thumbnail_url, checksum)
4. If value is a list → validate each item as FileEnvelope (for MULTI_UPLOAD,
   IMAGE_DROPZONE multi-mode)
5. MIME side-channel ({field_id}__mime) remains supported as fallback for
   legacy FILE/IMAGE string values
```

**JSON Schema output:**

```json
{
  "type": "object",
  "format": "file-envelope",
  "properties": {
    "filename": {"type": "string"},
    "content_type": {"type": "string"},
    "size": {"type": "integer", "minimum": 0},
    "blob_ref": {"type": ["string", "null"]},
    "data_url": {"type": ["string", "null"]},
    "thumbnail_url": {"type": ["string", "null"]},
    "checksum": {"type": ["string", "null"]}
  },
  "required": ["filename", "content_type", "size"]
}
```

For dual-read, FILE/IMAGE would use `_UNION_SHAPES` to emit:
```json
{
  "oneOf": [
    {"type": "string"},
    {"$ref": "#/definitions/FileEnvelope"}
  ]
}
```

### Edge Cases & Error Handling

- **Legacy string value submitted for FILE/IMAGE**: Accepted, no transformation.
  Validators skip FileEnvelope-specific checks.
- **Oversized file**: 413 from upload endpoint. `data_url` set to `null` if file is
  accepted but over `max_inline_size_bytes`.
- **MIME mismatch**: 415 from upload endpoint if `detected_mime` not in
  `allowed_mime_types`.
- **Blob storage failure**: 500 with diagnostic. `data_url` may still be populated
  (file content is in memory) — decision: still return 500, don't half-persist.
- **Thumbnail generation failure**: Non-fatal. `thumbnail_url` set to `null`, warning
  appended to response.
- **Checksum mismatch on re-download**: Detectable by consumer comparing stored
  checksum. Not validated server-side on submission — informational only.
- **IMAGE_DROPZONE legacy {name,type,size,dataUrl}**: Coercer maps to FileEnvelope:
  `name→filename`, `type→content_type`, `size→size`, `dataUrl→data_url`,
  `blob_ref→null`.
- **MULTI_UPLOAD legacy {answer,blob_ref,display}**: Coercer maps to FileEnvelope:
  `display→filename`, `answer→data_url (if string)`, `blob_ref→blob_ref`,
  remaining fields→null.
- **Empty file upload**: 400 — "No file content" (same behavior as existing REST
  upload handler).
- **Multiple files for single-cardinality field (FILE, IMAGE)**: 400 — "Field
  accepts a single file, received N".

## Parallelism Assessment

- **Internal parallelism**: **Yes** — this feature decomposes into independent layers:
  1. **Model layer** (FileEnvelope model + FieldConstraints extension) — no dependencies
  2. **Upload handler** (new endpoint + route registration) — depends on (1)
  3. **Validator updates** (dual-read coercer) — depends on (1)
  4. **JSON Schema renderer** — depends on (1)
  5. **Other renderers** (html5, pdf, xforms, adaptive_card, telegram) — depends on (1),
     independent of each other
  6. **Builtin controls + field_helpers** — depends on (1)
  7. **Tests** — depends on (2)+(3)+(4)

  Tasks 4, 5, and 6 can run in parallel after (1) is done. The five renderer
  subtasks in (5) are each independent.

- **Cross-feature independence**: Low conflict risk. The main shared files are:
  - `validators.py` — frequently touched but this feature modifies specific sections
    (FILE/IMAGE coercion, IMAGE_DROPZONE/MULTI_UPLOAD validation)
  - `jsonschema.py` — `_TYPE_MAP` and `_UNION_SHAPES` dicts are append-only
  - `constraints.py` — adding a new field is append-only
  - `routes.py` — adding a new route is append-only

- **Recommended isolation**: `per-spec` — all tasks sequential in one worktree.
  The model layer (1) is foundational and everything depends on it. While the
  renderer tasks are internally parallel, they each touch one line in `_TYPE_MAP`
  and a small section in their respective renderer — the coordination overhead of
  separate worktrees outweighs the parallelism benefit.

- **Rationale**: The dependency on FileEnvelope (task 1) is deep — every other task
  imports and uses it. A single worktree with sequential execution avoids merge
  conflicts on shared files (validators.py, jsonschema.py) and keeps the
  implementation coherent.
