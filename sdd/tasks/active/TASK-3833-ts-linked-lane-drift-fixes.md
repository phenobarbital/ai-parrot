## Context

Spec §3 Module 3, plus §9 S3 (consume the refresh response, surface warnings) and §9 S7 (identical
multiquery frame selection across lanes). Goal G3 is Python↔TS parity: for the same descriptor and params,
`execute_sources` and `LinkedLane` must produce identical conditions and rows. The research found silent
drift (F015):

- `deriveConditions` emits `limit` and emits `_offset: 0`; Python's `derive_conditions` does neither.
  The shared `limit_offset.json` fixture already expects no `limit`, so `conditions.test.ts` is red today.
- `setParam` accepts names the source never declared; Python's `_conditions_for` ignores them.
- `selectFrame` silently falls back to `result` / `[]`; Python's `_select_multi_frame` raises.
- `serverRefresh` posts `{params: {}}` (so it reverts to stored placeholders, §7 gotcha) and discards the response.
- Error notices say "data as of never" even when the descriptor carries a `snapshot_at`.

The vitest suites have never actually run (the pytest wrappers skip without `node_modules`), so this task
starts by recording a real baseline. M8 (parity) and M6 (canvas wiring) build on this contract.

```ts
/** Raised when a keyed MultiQuery payload cannot be reduced to ONE frame — TS twin of the RuntimeError raised by
 *  `QuerySlugSource._select_multi_frame` (query_slug.py:238). The lane reports status 'error' and keeps rows. */
export class FrameSelectionError extends Error {
  constructor(public readonly slug: string, message: string) {
    super(message);
    this.name = 'FrameSelectionError';
  }
}

/** Normalise a QuerySource payload to one row array, rule-for-rule with `_select_multi_frame`. */
function selectFrame(payload: unknown, src: LinkedDataSource): Row[] {
  if (payload === null || payload === undefined) return [];
  const frames: Record<string, unknown> =
    Array.isArray(payload) ? { result: payload } : typeof payload === 'object' ? (payload as Record<string, unknown>) : {};
  const keys = Object.keys(frames);
  if (keys.length === 0) return [];
  let selected: unknown;
  if (src.multi_output) {
    if (!Object.prototype.hasOwnProperty.call(frames, src.multi_output)) {
      throw new FrameSelectionError(
        src.slug,
        `multi-query slug '${src.slug}' has no output named '${src.multi_output}' (available: ${[...keys].sort().join(', ')})`,
      );
    }
    selected = frames[src.multi_output];
  } else if (Object.prototype.hasOwnProperty.call(frames, 'result')) {
    selected = frames['result'];
  } else if (keys.length === 1) {
    selected = frames[keys[0]];
  } else {
    throw new FrameSelectionError(
      src.slug,
      `multi-query slug '${src.slug}' returned multiple outputs (${[...keys].sort().join(', ')}); specify multi_output`,
    );
  }
  return Array.isArray(selected) ? (selected as Row[]) : [];
}
// REPLACE the comment at :48 (occurrences: 1, verified: grep -c 'deriveConditions never emits `limit`' linked/fetch.ts):
  // deriveConditions never emits `limit` (conditions.py:17-37 parity); the lane re-applies request.limit as
  // querylimit, bounded by the cap (S8/AC17) — the same rule as executor._conditions_for.
```
**Why**: an array payload is treated as `{result: array}` exactly as Python wraps a bare DataFrame, so a
declared `multi_output` other than `result` against a one-frame response errors in both lanes.
