## Context

Spec §7 Known Risks states that the cleanup procedure "is documented in `docs/`", and
spec §8 Q4 resolved the aggregate quota as **reporting only** — which makes the
runbook the *only* mitigation against disk growth. This task writes it.

Two deployment facts must be stated plainly, because getting either wrong silently
breaks handles rather than erroring: the store's root has to be on **shared,
persistent** storage (the server runs under gunicorn with multiple workers, and an
upload and its later attachment can land on different ones), and nothing deletes
files automatically.

Files uploaded in a session — or imported from remote storage, or generated by an

## Deployment requirement: shared, persistent storage

The server runs under gunicorn with several workers. An upload may be handled by one
worker and the later attachment by another, so the store's root MUST be on storage all
workers share, and it must survive a restart. On worker-local or ephemeral storage,
handles resolve intermittently or not at all — and the failure looks like a missing
file, not a misconfiguration.
