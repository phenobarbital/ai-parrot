## Context

Fourth defect of ledger `issue:b2c54218dcef`: *"SessionFileToolkit is not
registered on any agent, so sf_list_session_files is unreachable until wired."*

`SessionFileToolkit` is never instantiated or named anywhere outside its own
module and its tests — it is absent from `parrot_tools.TOOL_REGISTRY` (the
name → dotted-path map agents declare toolkits through) and from
`parrot.tools._LAZY_CORE_TOOLS`. Meanwhile `jiratoolkit.py:465` and `:591` tell
the model its handles come "from `sf_list_session_files`" — a tool no agent can
currently be given. FEAT-639's delivered value is inaccessible until this lands.

## Implementation Notes

### Key Constraints
- The lazy map exists so `parrot.tools` does not import every tool module at
  startup — add a `_LAZY_CORE_TOOLS` entry, never a top-level
  `from .session_files import SessionFileToolkit`.
- `TOOL_REGISTRY` points at `parrot.tools.session_files`, not a `parrot_tools.*`
  path: the toolkit lives in the **core** package, exactly like the neighbouring
  `file_manager_toolkit` and `obsidian` entries.
- This task is file-disjoint from TASK-4144/4145 and runs alongside them; it must
  not touch `session_files.py`.

## Implementation Blueprint

### Steps (in order)
1. Add the `TOOL_REGISTRY` key next to `obsidian` — *why*: the core-package
   entries are grouped there, and alphabetical order is not maintained in this map.
2. Add `SessionFileToolkit` to `__all__` and `_LAZY_CORE_TOOLS` — *why*: `__all__`
   alone does not make the attribute resolvable; the lazy map is what
   `__getattr__` consults.
3. Write the resolution test — *why*: an unused registry string is exactly the
   kind of entry that rots silently; the test imports it for real.

unresolvable name or an undocumented one.
